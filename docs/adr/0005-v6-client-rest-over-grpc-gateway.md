# 5. v6 client: REST over grpc-gateway, generated from api-schema-public OpenAPI v3

Date: 2026-11-10

## Status

Accepted

## Context

The 1.x SDK reaches v6 APIs over gRPC with stubs compiled at build time, and only for two services
(synthetics v202202, cloud_export v202101beta1). `api-schema-public` (pinned at
`5d1d2fa374e40d15646a495eed5b53e88b407713`, 2026-11-10) now defines 44 packages and 60 package versions; 50 versions
expose REST bindings, 318 operations in total. Hand-writing clients for that surface is not maintainable.

Every Kentik v6 service is a gRPC service with `google.api.http` bindings, served as REST/JSON by
grpc-gateway on the same hosts (`grpc.api.kentik.com`, `grpc.api.kentik.eu`). The repository ships
OpenAPI 3.0 specs (`gen/openapiv3`) for all of them. Facts checked for this decision:

- Auth: the specs' `securitySchemes` declare API-key headers `X-CH-Auth-Email` and
  `X-CH-Auth-API-Token`; the 1.x gRPC code sends the same keys as metadata (lower-cased, as gRPC requires).
- `kentik-api-proto`, the Python stub package defined in api-schema-public's `pyproject.toml`, is **not on
  PyPI** (404). It also pins `grpcio==1.47.0` and `protobuf>=3.20.3`, which are out of date. Option (b) would
  therefore mean compiling and shipping our own stubs for every service.
- Three stable services have **no REST bindings** (gRPC only): `deviceconf/v202511`, `diagnostic/v202501`,
  `kptr/v202602`. Their OpenAPI files contain types but no paths.
- Server-streaming RPCs exist only in those gRPC-only services (and `monitoring/v1`, which has no service).
- Pagination is offset/limit, either as query parameters (`limit`/`offset`, `pagination.limit`/`.offset`,
  `search.limit`/`.offset`) or as a `pagination` object in the request body; responses carry a list field and,
  in alerting, `pagination.hasMoreResults`/`totalCount`.

## Options

**(a) REST over grpc-gateway**, models generated from `gen/openapiv3` with datamodel-code-generator
(pydantic v2), service wrappers generated by our own script, transport on httpx.
- Pure-Python install (httpx, pydantic); no native wheels needed for the new client.
- Sync and async from one transport layer (`httpx.Client` / `httpx.AsyncClient`).
- Readable, typed models with docstrings from the schema; JSON is easy to log and mock (respx).
- Cannot reach gRPC-only services; no streaming.

**(b) gRPC with grpcio**, stubs generated from the protos.
- Reaches every service, including streaming.
- Native dependency (grpcio) and protobuf runtime/gencode version coupling; protobuf messages are less
  ergonomic than pydantic models; async needs a separate `grpc.aio` code path; harder to mock offline.
- The prebuilt package does not exist on PyPI, so we would generate and ship stubs anyway.

## Decision

Option (a).

- One client per flavour: `kentik_api.KentikClient` and `kentik_api.AsyncKentikClient`
  (`kentik_api.v6`), sharing configuration, retry, error and pagination code.
- Every service version with REST bindings is generated:
  - stable versions as `client.<service>_<version>` (e.g. `client.synthetics_v202309`; nested packages use
    `_`: `client.alerting_public_v202611`), plus an alias `client.<service>` for the newest stable version;
  - alpha and beta versions only under `client.experimental.<service>_<version>`, with an alias
    `client.experimental.<service>` for services that have no stable version.
  - If the newest stable version no longer contains a gRPC service that an older stable version has (today
    only `alerting/public`: v202611 has SuppressionService only), the alias combines the newest version of
    each gRPC service. The versioned attributes are always exact.
- Each version namespace exposes one attribute per gRPC service (`client.synthetics.synthetics_admin`), and,
  when method names do not collide across its gRPC services, the methods directly
  (`client.synthetics.list_tests()`).
- Models are forward-compatible, following ADR 0003: every field optional (protojson omits default values),
  unknown fields kept (`extra="allow"`), enums are open (unknown values become pseudo-members instead of
  validation errors). Fields are snake_case with the JSON (camelCase) names as aliases; both are accepted.
- Generation is driven by `scripts/generate.py` from the vendored `schema/openapiv3` snapshot; output is
  committed, and CI checks for drift. `kentik-api.json` is generated from the same data.
- Retries: 429 for every call (the request was not processed); 5xx and transport errors only for idempotent
  calls (GET, PUT, DELETE, and POST RPCs whose name starts with Get/List/Search/Query/Fetch/Find); exponential
  backoff with full jitter; `Retry-After` honoured.
- gRPC-only services (`deviceconf`, `diagnostic`, `kptr`) are listed in `kentik-api.json` as not reachable
  through this client. Adding them over gRPC (the package already depends on grpcio for the 1.x clients) is a
  separate decision.

## Consequences

- New runtime dependencies: `httpx`, `pydantic>=2`. grpcio and protobuf stay for the deprecated 1.x clients
  and can move to an extra in the next major version.
- int64 values are JSON numbers in the models (protojson emits them as strings; pydantic coerces), uint64
  fields are strings as declared by the schema.
- The client surface follows the schema exactly; a schema bump is a reviewable diff of generated code.
- No streaming support until a REST-reachable streaming RPC exists or gRPC transport is added.
